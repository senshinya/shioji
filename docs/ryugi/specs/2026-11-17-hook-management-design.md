# 已有 Hook 管理与信任批准

状态：2026-11-17 用户验收双页面设计并授权实现；原生功能与所属 worker 链路已接入，验证结果见 docs/hooks.md 和本地 verify/hook-management。范围由用户于 2026-11-17 确认：先补已有 hook 的管理和批准。

## 目的与范围

让用户在 Shioji 内看清所属设备、Agent 与工作目录发现的 hook，检查来源与执行定义，逐项启停、批准首次出现或已修改的定义。当前仅有 hookPrompt 上下文展示，测试通过手写隔离配置中的信任哈希绕过了应用缺失的管理入口。

本轮不新增、编辑、删除 hook 定义，不安装插件，不提供批量信任或跳过信任检查。信任定义与命令执行审批保持独立：管理操作不会回答会话中的执行授权，也不会授予项目或设备访问权。批准绑定的是原生运行时定义哈希，不宣称审核了脚本文件的全部内容或未来行为。

下列未由用户明确指定的入口、契约和交互均为本次建议；沿用 Go、MyGo、owning worker、harness-neutral 边界与冻结的视觉规范。

## 用户可见行为

1. 全局管理在设备 → Agent → Hooks，放在 MCP 之后、高级之前；保留现有 Skills Tab 与其他顺序。该页仅列当前设备/Agent 的全局用户、插件、系统与策略来源。全局发现须可靠排除项目层，不能拿目录 `/` 的查询结果冒充全局目录；不能可靠发现时明确不可用。
2. 工作区管理在工作区设置 → Hooks，与现有 Skills、MCP 使用同一页结构。按该工作区主目录发现项目来源，并分组显示继承的全局来源；只有项目项在此提供启停和信任。继承项显示启用/停用状态并只读，组尾“管理”及详情“在设备设置中管理”跳转全局页。托管来源始终只读。工作区附加目录不自动成为执行目录，归档工作区不为查看而创建环境。
3. 两个页面均有搜索、刷新和可滚动列表，不再提供查看范围选框。工作区页绑定所属设备和当前 Agent；只有多个可用 Agent 时沿用 Skills 的 Agent 选择，不提供独立设备覆盖。不要新增静态说明或重复页面标题。
4. 每项以事件、来源、命令/MCP 工具和信任状态为信息，固定来源、状态与操作列，控件对齐首行。保留 64 DIP 两行密度及共用滚动槽右边界。状态为“待审核”“已修改”“已信任”“策略管理”；已修改仍需重新审核，启用状态不等于信任状态。
5. 详情直接展示事件、完整执行命令或 MCP server/tool、来源路径及匹配/执行条件；设备、执行目录、类型、超时、完整指纹等放在“详细信息”。仅可管理来源在底部显示启用和“信任此版本”。未知类型或缺失审核信息的条目只能查看。批准不顺便启用，启用也不批准不可信定义。用户/项目/插件声明不改写，状态按所属设备的 Agent 原生用户配置持久化。
6. 从工作区/会话进入全局管理后，返回恢复原 Agent、查询、详情、滚动和普通草稿，并通过权威刷新反映全局项的新状态；不以旧页面快照覆盖新状态。管理跳转不切换会话执行目录或改变工作区归属。
7. 首页/会话的运行配置菜单保留 Hooks 入口和启用且待审核的计数。会话内按当前已接纳目录和真实运行时查看，项目项可操作，全局继承项进入设备页管理。首页查询实际选定执行目录；未创建 worktree 的结果只作基于主目录的预览，提交后按实际目录核对。存在且支持 thread-scoped 检查时使用那个进程；未加载/归档会话仅显示配置来源，不创建或恢复会话，不冒充当前加载状态。
8. 加载/刷新保持当前列表、查询与选择；断开后旧数据只读，恢复后重新检查。空状态为“没有 Hook”，搜索空状态为“没有匹配的 Hook”。错误与恢复操作按实际出现，成功以状态变化反馈；迟到结果不能跨设备、Agent、目录或会话回填。

## 中立契约与 worker

在 domain 中增加 typed HookCatalog、HookEntry、HookInspectionScope、HookChange 与 HookChangeResult，harness 层增加可选 HookProvider。Capabilities 分别表明查看、启停、信任以及实际会话检查能力； UI 不判断 Codex 名称。

Entry 包含不透明 HookRef、DefinitionRevision、已发现的展示信息、Enabled、TrustState、Managed、允许的操作及只读原因。具体字段与枚举组织由实现者确定；不得携带原生协议对象、任意配置 map 或让共享代码解析 Codex key/hash。目录范围与加载状态独立表达，不能用 enabled 推导已经在会话生效。

worker 提供版本化的 runtime.hooks.list/change 与能力协商。客户端传 workspace/session 身份，worker 从自己的持久化记录解析 owning device、Agent、目录和现有 source runtime；不接受任意客户端路径或配置文件目标。全局管理只允许当前已启用 Agent。会话/工作区/Agent 不匹配或已失去访问权必须拒绝。

管理页面范围作为 typed 全局/工作区范围进入 worker 校验。adapter 按真实配置来源声明条目归属和允许操作；共享层不按原生 key 或路径拼写推断。全局页面只可修改全局项，工作区页面只可修改该目录的项目项；继承项的直接变更须拒绝，不能只隐藏 UI 控件。全局状态按原生语义在工作区共享，不能复制成工作区覆盖或本地信任副本。

change 只支持 setEnabled 和 trustDefinition，带稳定 OperationID、HookRef、DefinitionRevision 和列表修订。worker 以设备内该 harness 的配置修改锁串行接纳，与其他原生配置写入共用实际写入边界。adapter 重新发现相同范围、核对当前定义及原生用户配置版本，只更改该项对应字段。外部文件变化不能靠进程内锁防止：批准精确旧哈希而不生成“始终信任”状态，新定义仍由原生引擎拒绝运行。

操作记录与结果查询使用现有持久化操作机制。保存回执丢失时重连查询并重新读取，不能自动批准最新版本；不确认结果时显示“结果未确认”，重复 OperationID 不产生新的授权。新操作必须来自用户重新检查后的动作。修改后刷新相关目录/会话观察，不能沿用旧 trusted 标记。

## Codex 适配

接口及字段名称全部留在 internal/harness/codex。使用真实安装版本的生成 schema 探测 hooks/list（cwds，支持时 threadId）与 config/read、config/batchWrite；不能仅按 CLI 版本号推断。新增可选接口不足不影响普通会话可用性。

hooks/list 是发现与 trustStatus/currentHash 的权威来源。key 仅用于 adapter 内定位，按 quoted TOML key path 编码。更改 hooks.state.<key>.enabled 或 trusted_hash，使用 config/batchWrite 的 filePath、expectedVersion 与精确字段 edit，保留其他状态和未编辑的私密配置，不重写 hooks.json、项目配置或插件文件。配置被高优先级覆盖则不报告成功。完整定义不可可靠展示的类型只读；command 与 MCP handler 是当前确认的审核类型。

写入原生用户配置后的“已保存”与各会话“已采用”分开。实现前用隔离真实 app-server 验证 reloadUserConfig 对已有独立进程的实际效果；禁止为了采用状态而中断、重启活动轮或执行用户 prompt。允许的最小延后边界是下一轮提交/恢复前原生配置重载，需按当前独立 session runtime 核对；在无法确认时显示“已保存，当前会话尚未确认”，不得把目录查询结果当成旧进程的已采用证据。应用不能让配置更新悄悄丢失或无限延期。

本次只读探查证据：本机 codex-cli 0.167.0 的 experimental schema 有 hooks/list；仓库冻结的 0.166.0 schema 也含 hook 发现、信任状态与线程范围字段。隔离 CODEX_HOME、无 thread 创建的真实 RPC 实测依次得到 untrusted → trusted；enabled=false；修改定义后 modified。该探查只证明发现和原生状态写入，不证明独立活动会话的采用时机或远程 UI。

## 已确认的界面稿方向

复用当前原生界面的侧栏、设备列表、Agent 全页配置与 32 DIP 内容边距。使用冷灰平面表面、13 DIP 正文、28 DIP 控件与薄分隔；不引入 Logo、蓝色选择填充或额外装饰。工作是让个人开发者核对已有设备自动化，界面性格保持克制、紧凑、可核对；视觉重点是实际命令和信任操作，无新增装饰性 signature。

- hook-list：设备 → Codex → Hooks。事件、状态、命令与来源组成列表，开关位于稳定的右侧列。搜索与刷新保持在滚动区外；该页只显示全局来源。
- workspace-hooks：工作区设置 → Hooks。项目项可启停和信任，继承全局项只读，通过“管理”进入设备页；返回保留工作区页面状态。
- hook-review：在同一 Tab 查看单项完整定义，底部固定启用与“信任此版本”，长元数据在中间滚动。托管项只读；信任与启用独立。
- session-entry：运行配置菜单显示 Hooks 和待审核数，原位弹层复用同一列表/详情，不跳离会话或清空草稿。

稿件均可切换亮暗，模拟断开、保存失败、定义变化与空列表。数据、命令和状态为示例，浏览器交互不执行 Hook 或写原生配置；最终 MyGo 布局与真实状态仍按验收章节核对。设计稿已由用户验收；原生实现仍须核对。

## 实施验证后的能力边界（2026-11-17）

- 当前原生 MCP Hook 元数据省略配置中的 input 参数。为避免用户在未看到完整执行定义时批准，工具型 Hook 暂时只读；命令型 Hook 可逐项启停与信任。这是实现审查后收紧的能力，不把 server/tool 名称冒充完整定义。
- HOME 也可能处于可信项目中。全局发现会先检查实际配置层；存在活动项目层时明确不可用。项目插件只有通过无项目层的独立全局发现确认归属才显示为全局继承，否则显示其他来源并只读。
- 未确认保存保留原请求和 worker 回执，刷新目录不被它永久阻塞。新动作必须来自用户对最新目录/定义的显式审核；不重放旧批准。
- 本机生产包完整测试、隔离活动会话和原生亮暗/窄窗口验证见 docs/hooks.md 与 verify/hook-management。远程实机和已安装签名包不属于已验证结果。
