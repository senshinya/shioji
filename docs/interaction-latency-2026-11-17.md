# 发送卡顿排查与客户端修复

2026-11-17，用户确认“没问题，commit and push”，验收本轮发送反馈与回执接续，并授权提交和推送。正式客户端尚未替换；本轮验收不执行客户端重启或设备升级。

## 现场

- 当前正式客户端：`/Applications/Shioji.app`，v0.3.5。只读采样显示主线程执行 `View.queueState → Model.EncodeState → JSON`；渲染和后台更新均会触发完整编码。
- 客户端状态文件约 4.85 MB，包含 25,783 个折叠键，其中 20,139 个是命令输出状态。未复制或改写正式客户端状态文件。
- MBP at Work 目录包含 27 个会话；经现有嵌入式 Tailnet 私有 SSH 桥，各做 6 次只读调用：`device.ping` 中位数 13.9 ms，`snapshot` 中位数 18.25 ms。短采样没有出现秒级网络延迟，不能排除偶发抖动或真实提交时 Git 校验耗时。
- 现有会话没有本地待发消息投影，动画与输入框交接等待 worker 消息或回执，复现了用户报告的触发顺序。

## 修改

- 现有会话复用新会话的本地发送投影，点击后开始动画、显示“正在发送”，保留稳定操作标识与持久草稿；worker 消息接管同一输入位置，不向权威历史写入临时记录。
- 等待期间允许独立编辑下一条草稿，确认／拒绝不覆盖已修改的草稿，结果未定时仍禁止重复发送。状态 footer 仅关联本次输入所属轮次，不接管以前的回复信息。
- 缓存未改变的折叠映射 JSON；较小的其他状态独立编码。状态变化生成新的不可变字节，保留异步保存与发送前落盘屏障。
- 原有发送曲线及工具阅读锚点测试，改为点击发送前建立历史和阅读位置，继续验证点击后的运动和跟随行为。

## 回执接续补查

用户要求进一步检查立即反馈后的回执接续。补查发现：事件流的确认已释放 `Pending`，但 UI 读取的最近操作列表未同步，导致临时状态过早清理。现有会话会重新挂载状态行，新会话在历史稍后加载时可能丢失本地消息投影和输入框运动。

已让已验证的中立操作事件同步到最近操作投影：更新既有操作，最多保留 100 条。UI 在释放待发记录后仍能读取实际确认结果，保持消息、状态行、Shimmer 与输入框的原有身份及运动；不延迟或改变 worker 的实际接纳。

- 64 组原生布局逐帧检查通过：新／现有会话、亮／暗模式、正常／减少动态效果，回执在 0、100、300、900 ms 到达，分别覆盖事件先到和命令回执先到。
- 核对消息和 composer 在同一动画时刻无跳位，编辑／复制槽位不移动，状态行不重新挂载，迟到回执不重启动画；另有“确认先到、历史稍后加载”的回归通过。
- 操作列表更新、去重与 100 条边界回归通过；客户端包完整测试及相关 race 检查通过。
- 真实 MyGo 原生窗口使用中立事件和命令回执的独立路径，采集修改前亮色、修改后亮色现有会话、修改后暗色新会话；确认事件约 1.2 秒、迟到命令回执约 1.7 秒、首段回复约 2.6 秒。画面由原生窗口的 `CapturePage` 采集，2400×1640、目标 12 fps、每段 65 帧，按实际间隔编码，无插帧。不是正式 worker 或模型调用，也不作为 60 fps 体感或性能 SLO 的证明。
- CUA 实际点击发送并观察两个修改后原生窗口；亮色窗口继续粘贴独立草稿，接续后保留内容与焦点。相关夹具进程均已退出。
