# 会话未知状态恢复 · 2026-11-06

本轮补齐 `unknown` 会话的原生处理入口，界面待验收。沿用 Go／MyGo、设备拥有的 worker 和 Codex 0.166.0 adapter，没有新增 UI 框架或运行时依赖。

## 行为与边界

- 输入框上方的恢复区域从所属设备读取 Codex `thread/read` 和分页 `thread/turns/list`，使用完整 items view。核对不调用模型、不提交原提示、不重建工具执行。
- 线程 ID 与已接纳执行目录必须一致。只有源 turn ID 和原始 `clientUserMessageId`／`userMessage.clientId` 的精确对应才能确认输入投递；不会按消息文字猜测。缺少历史、标识或完整分页时仍保留未知状态。
- 原 app-server 仍由当前 adapter 观察时，可以接回进行中的轮次。已确认完成、失败的历史会原位补齐；已有条目沿用 ID 和位置，原有请求回执不重建。保留已确认时间和每轮用量；源历史未提供的 token 字段保持未知。
- app-server 已退出时，自动核对和显式重试可以启动新的 app-server 来读取历史。启动前仍验证旧 PID 和进程开始时间。若记录表明旧进程存活，先显示「结束遗留进程」；单独确认后才向其专属进程组发送 TERM，然后再次证明旧进程已退出。不强杀无法验证的进程，不绕过不完整的启动记录。macOS 上的工具可能使用独立进程组，app-server 退出不代表工具已停止；重新读取的中断尾轮继续保持未知和 checkout 阻塞。只要任一目标轮次的工具停止状态未确认，后续完成轮次也不能解除这项保护。
- 无法读取源历史时，仅在该线程未绑定到当前 runtime，且此前 runtime 已被证明退出的前提下，允许在用户确认所属设备上的旧工具已停止后「手动结束旧轮」。结束遗留 app-server 本身不替代这项核对。该操作写入独立的 `abandoned` 状态，展示「已手动结束 · 结果未确认」，不伪造完成、中断或投递确认。
- 恢复事务包含历史、输入确认、操作结果和队列状态，并检查 session revision。派发和插队协程与恢复共用 worker 的串行边界，绑定接纳时的 runtime；延后调度不能复活已结束的操作或把输入投给新进程。剩余队列一直暂停；只有原有「继续队列」操作会授权继续。已手动结束的未知队列项仍保留，可编辑、删除或明确重试；不会悄悄重放。
- 「在新会话接续」只整理最近已保存的对话文本与未发送草稿到首页，保留原会话草稿、答案和队列。首页已有草稿也保留在接续草稿中。用户检查并发送非空内容后才创建新会话；新会话使用所选工作区当前的启动上下文。不会声称这是原线程或工具执行的无缝恢复。
- 恢复卡片与消息框同为 768px 阅读列，采用现有请求卡片的中性灰表面、12／14px 内边距和 8px 间距。高度与内容位移同步，包含入场、离场及内容换行造成的高度变化；无淡入淡出，尊重减少动态效果，保留原输入焦点。双会话中的接续操作也进入统一首页。

协议增加 minor 7 的 `session.reconcile`，action 为 `check`、`end`、`interrupt` 或 `stop-runtime`。请求带 session ID 与 revision；回执验证所属设备和 session，更新对应设备的 readiness；恢复命令的客户端超时为 25 秒，涵盖 worker 的 20 秒处理上限。旧 worker 显示更新提示，不发送不支持的恢复命令。没有修改数据库 schema、冻结稿或原设备权限。

## 自动核对与原会话继续

worker 启动、runtime 退出、消息投递结果不确定和客户端重新连接时会在后台读取源状态。每次连接首次 snapshot 触发一次复核；相同 revision 不会因普通刷新反复读取。空闲 runtime 退出也会恢复 readiness。核对不发送模型提示，不停止仍存活的旧进程。状态暂时不明时延迟 300ms 展示紧凑的 shimmer 状态行；只有需要用户处理时才展开卡片。临时查询失败可「重新核对」。

原历史可读，且最新本地用户输入已确认投递或能由源精确标识找回时，提供「继续原会话」。该动作需要用户点击，提交明确的继续提示，保留原 ThreadID 和已接纳 CWD；工作区主目录后来改变也不搬迁旧会话。最新输入未出现在源上下文时，仅提供可审阅的新会话接续草稿，避免误接续更早的任务。普通草稿与附件不被继续操作消费，剩余队列始终保持暂停，空队列的暂停标志也不会顺带解除。

插队投递结果不确定时统一将会话置为 unknown。晚到的 turn/completed 可以确认轮次结果，但不能掩盖尚未确认的输入投递；重启也会修复旧 completed + indeterminate 组合。

动画沿用现有消息、请求卡片的曲线与时长。状态行、卡片和继续入口共用实际内容测量；高度和 8px 间距分别插值，中途反向切换不会改变间距。内容无淡入淡出，减少动态效果时直接切换。继续消息从恢复操作所在行移入，始终保留正常阅读宽度，避免长文本被挤进按钮宽度。

## 面向普通用户的恢复流程

恢复卡片默认只显示「会话需要恢复」、草稿／队列保留说明和一个明确的「恢复会话」主操作。「查看处理方法」按需展开执行设备、工作目录和未完成工具记录；旧的「手动结束旧轮」退到高级处理。状态与任务详情沿用现有中性表面、13／12／11px 阅读层级、12／14px 内边距及 8px 间距。展开／收起与确认文案变化使用同一个实际高度动画，不淡入淡出；输入框位置、草稿和焦点保持，减少动态效果时直接切换。

worker 会在 app-server 存活时观察其新建的独立后代进程组，记录 PID、内核开始时间和已见成员。命令与会话的匹配只生成候选信息，不能证明这个进程属于当前工具项。详情显示经过身份验证的存活成员的实际 argv／PID 与进程组；不能读取实际命令或成员已跨组时保持未知，禁止选择。用户逐项选择后，再明确确认按组停止；默认没有选中项，也不会自动发信号。

协议 minor 8 增加候选进程信息及 `stop-tasks` 的显式 Targets 身份。服务端仅接受本 worker 私有记录中的目标，信号前重验开始时间和组归属，拒绝篡改、空选择、当前 worker 所在组及超时操作。新进程不能凭 PID 复用获得旧授权。成员身份不会因迁移进程组而从记录中消失，进程信息不可验证时保持未知。停止采样已退出的组，但保留磁盘证据；未捕获项短暂观察后退采样，不长期轮询完整会话目录。

停止所选组后仍保持 unknown 和 checkout 保护。命令可能启动未被观察到的独立后台进程，因此不能将「所选组已停止」当作「整个任务已停止」。用户还需独立确认其余后台任务已结束，才能在本地结束旧轮，随后提供原会话继续入口。所有步骤保留草稿和暂停队列，不自动提交继续提示。旧版遗留会话没有进程记录时，仍需人工确认，不能自动补造归属。

验证包括真实 Codex + 本地确定性服务制造仍存活的命令组、app-server SIGKILL 后记录保留、空／篡改 Targets 不停止进程、停止后提交仍被未知状态阻止、独立结束确认、跨组成员不被误判为已停止、超出首屏 100 条历史后的任务识别，以及停止后的退采样。长历史回归在恢复旧分页过滤的 overlay 下明确失败，当前实现通过。原生窗口实际走通完整流程，截图覆盖亮暗模式与 940px 窄窗口；model 请求数始终为初始夹具的 1 次，未向真实模型新增请求，草稿与 1 条暂停队列保留。

## 会话级 runtime 隔离与 macOS 崩溃验证

本次先按已确认方案验证进程边界，再实现可以安全成立的部分。每台设备仍只有一个 authoritative worker；执行中的会话分别使用独立 Codex app-server，原来的 adapter 仅保留目录／能力读取和历史核对。会话级 runtime 的创建记录位于私有 `runtimes/<sessionID>/runtime-process.json`，记录 session ID、PID 和内核开始时间，在初始化与线程创建前落盘。原应用 session ID、Codex thread ID、已接纳 CWD、草稿和队列不迁移、不重建。

提交先持久化接纳结果，后台启动对应 runtime，再验证原操作仍是 accepted 后派发；初始化不会占用提交回执的连接等待。插队、回答、停止和活跃历史读取都路由到该会话的 adapter。catalog 的重建不再清空其他会话的绑定。创建失败且确认没有启动进程时清除 Starting 标记，保留原输入并标记发送失败，允许明确重试；确有启动或归属无法确认时保留记录。显式重启作用于对应会话的自有根进程；旧版共享根保留单独的旧流程。

真实 worker SIGKILL 测试发现 `owner.lock` 的描述符被子进程继承，导致旧 worker 消失后新 worker 仍无法取得锁。增加 `O_CLOEXEC` 后，同一测试能够重新打开设备状态；未通过记录先于修复存在，修复后通过。此修复只影响以后启动的子进程，不会结束现有用户任务，也没有重启原 Mac／Air worker。

### 上一阶段未通过的自动清理前提

**上一阶段尚未实现完整工具托管；以下保留该阶段的验证结论，新托管边界见下一节。** 两个独立 app-server 可以隔离根进程，无法证明所有工具后代归属；macOS SDK 明确标注 NOTE_TRACK／NOTE_CHILD 自 10.5 起不再支持。普通 exec 工具会自行创建进程组，能够在 app-server SIGKILL 后继续执行。Codex 的完整分页历史也可能缺失已经开始的工具项，因此源历史和本地 started 事件都没有工具，并不能反向证明没有工具执行。试验中的无工具历史放行逻辑已删除，未进入最终实现。

当前自动核对仍能接回自己正在观察的 live turn，或补回源明确确认的 completed／failed 结果。无法确认的中断尾轮继续保持 unknown、checkout 保护和暂停队列。只清理通过 session＋PID＋开始时间确认的自有根，不自动停止候选工具，不把根退出当成全部工具已停止。要进一步消除这类人工处理，必须让工具启动经过可在执行前持久化归属的托管边界，并验证独立进程组／脱离后代；不能继续补轮询、命令匹配或缺失事件的推测。

恢复界面移除了初始「恢复会话」要求，后台复核一律使用紧凑进度行；只有核对确实失败／执行归属不明时显示「暂时无法继续」与「重试恢复／查看处理方法」。沿用同一高度、8px 间距和位移动画，不增加淡入淡出；普通草稿、焦点和暂停队列保持。亮色、深色和 940px 窄窗口实际截图为 `70`—`73`，来自本地隔离的真实 Codex＋确定性 Responses 服务，未录屏。

### 本轮测试与限制

- 两个真实 app-server 并行：A 的根被 SIGKILL 后，B 仍运行并正常完成；A 后台只读核对且保持 unknown，没有重新提交任何提示或队列。
- 整个独立 worker 被 SIGKILL 后重启：两会话的原 session／thread／CWD 和暂停队列保留，provider 请求仍只有原始两次。工具进程单独分组时不被错误宣称已停止。
- 会话丢失线程绑定时，明确停止只关闭该会话的根，另一会话与 catalog 均保持；关闭后仍保留工具结果未知，允许独立的人工结束确认。
- 已知未启动的 runtime 失败保留原输入，并可在恢复可执行文件后明确重试；不留下永久 Starting 锁死。
- 两个会话同时运行相同 shell 命令，可以分别显示自己的候选进程；依据各自 session 根与祖先链，取消跨独立根的全局“只有一个活动会话”门槛，仍不将候选升级为自动终止授权。

## 创建期托管执行与自动恢复（本次增量）

现在会话专属 app-server 与官方 `exec-server` 都由 worker 启动并持有。命令、PTY 命令和本地 stdio MCP 经过同一个原生启动握手：先记录 launch intent，再验证根进程、同组 anchor、内核开始时间及真实祖先关系并落盘，收到 worker ACK 后才执行目标程序。相关标识只用于关联，不作为进程归属凭据。目标环境与参数仅在内存握手中传递，不写入执行日志；bootstrap 与 anchor 使用干净环境，动态加载器变量在完成登记后才恢复。shell snapshot 暂停使用，避免在握手前执行 shell 状态。

Agent 或执行服务意外退出时，worker 先持久化 generation 保护并暂停队列，再封锁新执行和迟到的 ACK，关闭对应协议连接，清理已登记进程组并验证停止。迟到的 turn/completed 只能更新轮次记录，不能解除保护。完整源历史中的精确 client input 标识全部属于该已清理 generation 时，中断轮次可自动恢复为 interrupted；没有精确输入或归属凭据则继续保留 unknown。不会重放原提示或自动派发暂停队列。

worker 重启时接管所有磁盘 scope，包括已完成与空闲会话，清理其仍持有的 Agent、执行服务、MCP 与 anchor；不依赖执行服务短暂的逻辑重连保留期。正常结束的进程组会退休为 stopped receipt，今后不再把复用的 PID／PGID 当成旧身份。新 generation 清除上一代的 live 回收记录，避免快速接续被误判。丢失 manifest、身份变化、已知成员迁移或停止结果无法确认时保持保护。

**这里保证的是已登记进程组的清理，不是任意进程树的操作系统级 containment。** 真实回归确认：命令主动通过 setsid／新 session 脱离后的未登记进程不在此保证内。不能宣称所有任意后台进程必定清理；旧版未受管会话、外部执行环境及不完整覆盖仍保留原人工处理边界。hooks／plugins 不完整覆盖时不会出具整个轮次的托管清理凭据。

保留 Codex 原文件系统 sandbox 与审批策略。真实只读回归检查目标命令已运行并输出标记，同时写入被拒绝。当前启动握手尚未实现 managed network proxy／credential broker 对目标环境的完整变换；这类请求明确拒绝且不启动命令，不能静默忽略代理、恢复未遮蔽密钥或放宽网络权限。后续支持需单独验证。
