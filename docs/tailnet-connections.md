# Embedded Tailnet connections

Approved UI: local Ryugi `artboard/tailnet-setup`, welcome-tailnet, add-tailnet and network pages (2026-11-12).

Tailnet is transport, not a second device authorization system. Joining the embedded node and choosing a visible supported peer precedes the existing SSH preparation, host trust, key setup, worker deployment/update, Agent configuration and completion paths. Welcome additionally continues to workspace setup/import; adding a device returns to device details. Device/worker identity and catalogs remain authoritative and independent of route. No pairing codes or app-level grants.

The application owns an official tsnet node, independent of the system client. Its encrypted persistent state uses a random Keychain-held encryption key. Startup restores only a previously started identity; new enrollment/browser login requires user action. Authorization URLs remain transient and absent from logs/client JSON. Network management has no add-device entry.

## Device names and icons

Shioji's device display name and icon are client preferences. Renaming the display alias does not rename the node registered with Tailscale or change its worker identity. Network rows prefer a saved display alias; their expanded details retain the actual Tailnet name. The local network section also shows the display alias separately from its registered node name.

Clicking a device icon opens a compact palette containing only five icons: display, laptop, tablet, phone and server. No captions or hover tooltips are shown; accessible labels remain available. New devices receive a concrete initial selection using reported peer OS conservatively: display for macOS/Windows or unknown, phone for iOS/Android, tablet for explicit iPadOS, server for Linux. OS alone does not establish hardware form factor. Explicit selections persist and remain attached to the same logical device when a route is added/removed. Unsaved connection drafts keep their own icon selection.

Custom control-server selection is not yet a supported Shioji configuration: the application currently has no Headscale address field or persisted control-server choice. The underlying tsnet ControlURL facility does not by itself establish tested Headscale product support.

## Background network ownership

The GUI now uses a local network client; a separate `shioji-runtime --network-serve` process owns tsnet, inbound TCP forwarding and peer-specific SSH bridges. GUI/window cancellation closes only its subscription. The worker is a separate process and its update/stop or login-service switch does not control networking. Production uses the independent `dev.shioji.network.agent` user LaunchAgent in a signature-verified Runtime.app installed alongside the execution bundle; the current worker bundle is not overwritten or unregistered. Isolated profiles use a detached, signature-verified host without registering a system service. No before-login or after-logout connectivity is promised.

Private Unix IPC checks the peer UID; the GUI also verifies the host process and signed installation. Instance and client identifiers fence requests; monotonically increasing client operation sequences suppress duplicate mutations. A lost action response is queried, never automatically replayed. Authorization URLs are transient and delivered only to the initiating client. Client/session slots and SSH route listeners are bounded; idle routes are reclaimed without closing active streams.

An identity-directory flock guards new node owners. Profile-scoped GUI markers include process birth time, so older GUI owners are detected separately rather than assuming they obey the new lock. A matching old GUI must exit before migration. Native Keychain preflight reads the exact historical item and encrypted identity without changing either; the background host cannot open authorization prompts. Explicit reconnect can run a foreground preflight using the same signed host. An inaccessible, missing or damaged existing identity requires local user action and never creates a replacement node. Recoverable node startup failures back off; explicit pause/logout cancels retries and survives GUI/service restarts.

Only explicit Join/Reconnect can register or authorize a service. Pause, logout and forwarding changes do not implicitly start an unavailable host. A malformed/unreadable intent cannot leave a live control socket acknowledging commands without a node consumer. Legacy GUI profile detection recognizes both Go flag spellings (`-client-state` and `--client-state`, including `=value`).

Explicit reconnect checks the newly bundled host's build identity. A separate, bounded `--network-prepare` process performs candidate preflight, old network-host shutdown, new registration/start and readiness confirmation; cancelling or quitting the GUI does not cancel that critical section. The execution worker's registration is untouched. Selected host metadata is saved only after a verified ready response. Failed preflight preserves the old owner; a failed candidate launch restores the previous signed owner and confirms it is reachable before reporting failure. Revoked OS approval is respected rather than bypassed by rollback. Compatible running hosts are retained on ordinary app startup. Transient preparation results contain no credentials, use private atomic files and have bounded retention.

## Multiple routes per device

An authenticated worker DeviceID admits multiple stable routes, including SSH+SSH. Existing SSH/OtherSSH state migrates to Routes/ActiveRouteID without duplicating device/workspaces. Normal Add Device authenticates first, merges only matching worker identity, saves before compact success/existing feedback, and skips redundant Agent setup. A failed save restores the prior device config and keeps the entered route for retry.

Each route has an independent, bounded read-only probe channel. New workers provide side-effect-free device.ping; older workers use worker.info on both routes. Fresh median RPC RTT, minimum improvement, sustained observations and cooldown prevent jitter-driven switching. Only one business dispatcher/event source is authoritative. Same-generation handoff aligns journal sequence, preserves logical UI epoch, queries unknown accepted submissions without replay, and retries only an explicit read-only whitelist. Worker build/service metadata is refreshed on admission and handoff, including after an update.

Live multiple-route verification (2026-11-13): normal Add Device merged actual LAN IP and mDNS SSH paths into the same MBA. Terminating only this test client's active-path SSH bridges switched to the IP standby while retaining the same device and running remote worker. Native light/dark/narrow screenshots and regression/race tests accompany the original design. This run does not certify real SSH+Tailnet handoff: the new test executable's existing-node key lookup is rejected by macOS with -25308 although the login Keychain is unlocked. Existing identity and access controls were preserved.

Per-route details: Tailnet is labeled Tailnet SSH and shows its own effective OpenSSH user. A bounded background `ssh -G` expansion supplies user/hostname/port even while its node is paused; it does not connect, rewrite targets, inspect credentials, or infer another route’s user. Each route expands independently with existing height motion; shared DeviceID is separate. Tailnet network/path measurements resolve the displayed route’s peer, regardless of which route is active.
